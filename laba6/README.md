

# **ЛАБОРАТОРНА РОБОТА №6**

**Тема:** Реалізація міжсервісної взаємодії
**Мета:** Реалізувати зв’язок між двома сервісами за допомогою Kafka та Telegram бота



## **1. Теоретичні відомості**

Міжсервісна взаємодія є ключовим аспектом побудови розподілених програмних систем. Взаємодія між сервісами може бути:

1. **Синхронною** — через прямі запити до API (REST або gRPC). Недоліком є жорстке зв’язування: якщо один сервіс не працює, інші можуть зупинитися.
2. **Асинхронною** — через обмін повідомленнями або подіями за допомогою брокерів подій (Kafka, RabbitMQ, NATS). Перевагою є слабке зв’язування та масштабованість.

Для забезпечення надійності та відмовостійкості важливо враховувати:

* **Ідемпотентність операцій** — повторне отримання повідомлення не створює дублікати дій.
* **Гарантії доставки**:

  * *at most once* — повідомлення може загубитися, але не дублюється.
  * *at least once* — повідомлення гарантовано доставляється, можлива повторна обробка.
  * *exactly once* — повідомлення обробляється рівно один раз.
* **Обробку помилок і retry** — повторні спроби або переміщення у dead-letter queue.
* **Моніторинг черг** — швидкість обробки, кількість непрочитаних подій, час затримки.

У лабораторній роботі реалізовано асинхронну взаємодію між сервісами через Kafka, а Telegram бот виступає інтерфейсом для користувача.


## **2. Завдання до роботи**

1. Налаштувати Kafka як брокер подій.
2. Реалізувати обмін подіями між Telegram ботом і Kafka (публікація та підписка).
3. Продемонструвати обробку події у логах консолі (конс’юмер Kafka).



## **3. Протоколи розв’язання задач**

### **3.1 Telegram бот**

* Бот реалізує функції:

  * `/start` — запуск бота.
  * `/help` — перелік команд.
  * `/add` — додати нову вправу.
  * `/list` — вивести список вправ.
  * `/delete` — видалити вправу.
  * `/clear` — очистити всі вправи.
  * `/stats` — статистика вправ.

### **3.2 PostgreSQL**

* Використовується для збереження даних про вправи:

  * `chat_id` — ID користувача Telegram.
  * `name` — назва вправи.
  * `created_at` — дата додавання.

### **3.3 Kafka**

* **Producer** — публікує повідомлення про додавання або видалення вправ.
* **Consumer** — читає повідомлення і логувує їх у консоль.
* Використовується топік `workout_events` для обміну подіями.
* Гарантія доставки: *at least once* (повідомлення можуть повторюватися, але не втрачаються).



## **4. Протокол виконання**

1. Налаштовано `.env` файл з параметрами:

```
TELEGRAM_TOKEN=<токен_бота>
DATABASE_URL=postgres://user:password@localhost:5432/workout
KAFKA_BROKER=localhost:9092
KAFKA_TOPIC=workout_events
```

2. Запущено Kafka брокер та створено топік `workout_events`.
3. Запущено Telegram бота.
4. Додано, переглянуто та видалено кілька вправ.
5. Події успішно публікувалися у Kafka і оброблялися конс’юмером.


## **5. Висновки**

* Було реалізовано асинхронну міжсервісну взаємодію через Kafka.
* Telegram бот успішно взаємодіє з базою даних PostgreSQL та Kafka.
* Події про зміни у списку вправ коректно публікуються та обробляються, що демонструє event-driven підхід.
* Система готова до масштабування та інтеграції з іншими сервісами без жорсткого зв’язку.



## 6. Контрольні запитання
1. Що таке асинхронна взаємодія?
   Взаємодія сервісів без очікування миттєвої відповіді, через події або черги повідомлень.

2. Які системи повідомлень ви знаєте?
   RabbitMQ, Apache Kafka, NATS, Redis Streams.

3. **Як працює RabbitMQ?**
   Використовує черги повідомлень, де відправник і споживач не залежать один від одного у часі.

4. Що таке “publisher” і “subscriber”?

   * Publisher — публікує повідомлення.
   * Subscriber — підписується на повідомлення та обробляє їх.

5. У чому різниця між чергою та топіком?
   Черга: повідомлення доставляється одному споживачу.
   Топік: повідомлення доступне всім підписаним споживачам.

6. Як обробляти помилки у подійно-орієнтованих системах?
   Використовувати retry, dead-letter queue та ідемпотентну обробку.
