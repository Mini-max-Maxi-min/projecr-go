

# **ЛАБОРАТОРНА РОБОТА №1**

## **Аналіз вимог до розподіленої системи**

---

# **1. Мета роботи**

Навчитися визначати та формалізувати функціональні і нефункціональні вимоги до розподіленої програмної системи (РПС), визначати користувачів та їх взаємодію з системою, будувати діаграми контексту та прецедентів.

---

# **2. Теоретичні відомості**

Розподілена система — це сукупність незалежних обчислювальних вузлів (серверів, мікросервісів, мобільних пристроїв, IoT), які взаємодіють між собою через мережу і працюють як єдине ціле.
Кожен вузол виконує власну функцію: зберігання даних, обробка запитів, аналітика, взаємодія з користувачем.

Основні характеристики РПС:

* **Масштабованість** — можливість збільшувати продуктивність шляхом додавання нових вузлів.
* **Надійність** — система продовжує працювати при часткових збоях.
* **Доступність** — час, протягом якого система доступна користувачам.
* **Узгодженість** — коректний стан даних на всіх вузлах.
* **Безпека** — захист від несанкціонованого доступу.
* **Затримки** — швидкість відповіді системи.

У процесі аналізу вимог визначають:

* користувачів,
* зовнішні системи,
* функціональні та нефункціональні вимоги,
* взаємодію компонентів.

---

# **3. Предметна область**

У цій лабораторній роботі предметною областю обрана **розподілена система Workout Tracker** — сервіс для відстеження тренувань користувача з використанням Telegram-бота, серверного API, бази даних та можливих IoT-фітнес пристроїв.

Система призначена для:

* ведення списку вправ,
* збору тренувальних даних,
* аналізу активності,
* формування статистики.

Часткова реалізація — Telegram Bot + PostgreSQL.

---

# **4. Користувачі та точки взаємодії**

## **Користувачі**

| Роль                  | Опис                                                      |
| --------------------- | --------------------------------------------------------- |
| **Користувач (User)** | Виконує вправи, додає їх у систему, переглядає статистику |
| **Тренер (Coach)**    | Аналізує дані спортсмена, формує плани                    |
| **Адміністратор**     | Контроль системи, управління доступами                    |
| **IoT/Fitness API**   | Передає сенсорні дані з фітнес-браслетів                  |

## **Точки взаємодії системи**

 Telegram Bot
 REST API
 PostgreSQL база даних
 IoT/Fitness API (Apple Health, Google Fit)
 Інтерфейси майбутньої веб-адмінки

---

# **5. Функціональні вимоги**

### **Telegram Bot**

* додавання вправи командою /add;
* перегляд списку вправ /list;
* видалення вправ /delete;
* очищення списку /clear;
* статистика /stats.

### **Система**

* зберігання даних у PostgreSQL;
* обробка CRUD операцій;
* розрахунок статистики;
* логування та обробка помилок.

---

# **6. Нефункціональні вимоги**

### **Масштабованість**

* підтримка горизонтального масштабування API через Docker/Kubernetes;
* можливість обробки 10 000+ користувачів.

### **Надійність**

* система працює при часткових збоях;
* відновлення після збоїв (retry, reconnect).

### **Безпека**

* захист токенів у .env;
* шифрування трафіку HTTPS;
* контроль доступу та ізоляція сервісів;
* рольова модель доступу (User, Coach, Admin).

### **Продуктивність**

* середня затримка відповіді ≤ 300 мс;
* виконання SQL-запитів ≤ 100 мс.

# **9. Контрольні запитання**

### **1. Що таке розподілена система?**

Система, що складається з кількох незалежних вузлів, які взаємодіють через мережу та працюють як єдине ціле.

### **2. Які типи архітектур використовуються?**

* клієнт–сервер
* мікросервіси
* SOA
* P2P
* event-driven
* serverless

### **3. Що таке функціональні та нефункціональні вимоги?**

Функціональні — що система робить.
Нефункціональні — як система працює.

### **4. Як визначають користувачів і сторони?**

На основі ролей, сценаріїв використання, взаємодій і зовнішніх систем.

### **5. Що таке контекстна діаграма?**

Діаграма найвищого рівня, що показує зовнішніх акторів і взаємодію з системою.

### **6. Типові ризики?**

* мережеві затримки
* відмова вузлів
* втрата узгодженості
* безпека
* брак масштабованості

### **7. Як вимоги впливають на архітектуру?**

Наприклад:

* масштабованість --> мікросервіси
* надійність --> реплікація
* низькі затримки --> event-driven
* безпека --> розмежування доступу
